2. Line-by-line diffing two similar code paths — I gave it `add_to_playlist()` and `rate_song()` side by side for Issue #4 and asked what structurally differed between them, which is what confirmed the notification call was simply absent from `rate_song()` rather than present-but-broken.

**Where I had to verify or override the AI.** Issue #3 is the clearest example of not trusting an explanation without checking it. Separately, while writing a regression test for Issue #4, I found (through the test itself failing, not through AI) a real but out-of-scope bug in `add_to_playlist()` — its `playlist.songs.append(song)` call doesn't populate the NOT NULL `position`/`added_by` columns on the `playlist_entries` association table. I did not fix that, since it isn't one of the 5 tracked issues, but I noted it and adjusted the affected test to route around it rather than silently ignoring the failure.

## Codebase Map

### Main files and their roles

- **`app.py`** — Flask application factory (`create_app`). Configures the SQLAlchemy `db` object, wires up SQLite (`mixtape.db` by default, overridable via `DATABASE_URL`), registers the four blueprints (`songs`, `playlists`, `users`, `feed`), and calls `db.create_all()`. This is the only place the Flask app object is built — routes and services both import `db` from here, which is why `app.py` has to be imported before `models.py` (and why running `python app.py` double-imports and breaks SQLAlchemy).
- **`models.py`** — All SQLAlchemy models: `User`, `Tag`, `Song`, `ListeningEvent`, `Rating`, `Playlist`, `Notification`, plus three association tables (`friendships`, `song_tags`, `playlist_entries`). Notable design choices:
  - `friendships` is a *symmetric* many-to-many table — seeding a friendship requires inserting both `(u1, u2)` and `(u2, u1)` rows (see `seed_data.py::add_friendship`).
  - `playlist_entries` is not a bare join table — it carries `position`, `added_by`, and `added_at` columns, so playlist order and provenance live on the association row, not on `Song` or `Playlist`.
  - Every model has a `to_dict()` used directly by routes for JSON serialization — there is no separate serializer/schema layer.
- **`routes/`** — Thin Flask blueprints. Every route: parses `request.args`/`request.get_json()`, calls exactly one service function, and either returns `jsonify(...)` or catches `ValueError` and returns a 4xx. No business logic lives here.
  - `songs.py`: `/songs/search`, `/songs/<id>`, `/songs/<id>/rate`, `/songs/<id>/listen`
  - `playlists.py`: `/playlists/` (create), `/playlists/<id>`, `/playlists/<id>/songs` (GET/POST)
  - `users.py`: `/users/<id>`, `/users/<id>/streak`, `/users/<id>/notifications`, `/users/notifications/<id>/read`
  - `feed.py`: `/feed/<id>/listening-now`, `/feed/<id>/activity`
- **`services/`** — All business logic. This is where the five bugs live, per the README.
  - `streak_service.py`: `record_listening_event()` creates a `ListeningEvent` and calls `update_listening_streak()`, which compares `today` vs `user.last_listened_at.date()` to decide whether to no-op, increment, or reset the streak.
  - `feed_service.py`: `get_friends_listening_now()` pulls each friend's most recent `ListeningEvent` within a recency window; `get_activity_feed()` is the unfiltered version (last N events regardless of age).
  - `search_service.py`: `search_songs()` does a case-insensitive `ilike` match against `title`/`artist`.
  - `notification_service.py`: `create_notification()` is the single low-level constructor. `add_to_playlist()` and `rate_song()` are the two "something happened to your song" entry points that are supposed to call it.
  - `playlist_service.py`: `get_playlist_songs()` joins `Song` to `playlist_entries` and orders by `position`.
- **`seed_data.py`** — Drops and recreates the DB, then inserts 5 users with real friendships, 25 songs (deliberately split into 0-tag / 1-tag / 3+-tag groups — the 3+-tag group is what exposes Issue #3), 3 playlists, and a mix of recent (<30 min) and older (1–14 day) `ListeningEvent` rows so both feed functions have realistic data to filter.
- **`tests/`** — `test_streaks.py`, `test_search.py`, `test_playlists.py` already exist and directly encode the expected (bug-free) behavior for Issues #1, #3, and #5 — e.g. `test_streak_increments_on_sunday` asserts a Sunday listen should *increment* the streak, not reset it. Running `pytest` before touching any code is effectively free reproduction for those three issues.

### Data flow — a friend rates your shared song (Issue #4's territory)

1. Client sends `POST /songs/<song_id>/rate` with `{user_id, score}`.
2. `routes/songs.py::rate()` parses the body, validates `user_id`/`score` are present, and calls `notification_service.rate_song(user_id, song_id, int(score))`.
3. `services/notification_service.py::rate_song()`:
   - Loads the `Song` and the rating `User`, raising `ValueError` (→ 400) if either is missing.
   - Looks up any existing `Rating` row for `(user_id, song_id)` (there's a `UniqueConstraint` on that pair in `models.py`) — if found, updates its `score` in place; otherwise inserts a new `Rating`.
   - Commits and returns the `Rating`.
4. Route returns `rating.to_dict()` as JSON with a 201.

Compare this to the sibling flow, adding a song to a playlist:

1. `POST /playlists/<id>/songs` → `routes/playlists.py::add_song()` → `notification_service.add_to_playlist()`.
2. `add_to_playlist()` appends the song to `playlist.songs`, commits, **then** calls `create_notification(user_id=song.shared_by, notification_type="song_added_to_playlist", body=...)` — but only if the adder isn't the original sharer.

`rate_song()` has no equivalent last step. It saves the `Rating` and returns — it never calls `create_notification()` at all. That asymmetry (one entry point calls the shared notification constructor, the sibling entry point simply forgets to) is the shape of Issue #4, and it's a structural/architectural gap rather than a typo: the function that's supposed to make the call just doesn't exist yet.

### Patterns noticed

- **Routes are dumb, services own logic.** Every route file follows the same three-line shape: parse input → call one service function → `jsonify` or catch `ValueError`. This makes tracing a bug from an endpoint trivial — the route always points at exactly one service function.
- **No timezone-naive datetimes** are supposed to leak into comparisons — models default `datetime.now(timezone.utc)`, and `streak_service.update_listening_streak` explicitly re-attaches `timezone.utc` to `last_listened_at` if it comes back naive from SQLite. Despite that care, date/time *boundary* logic (day boundaries, week boundaries, "recent" windows) is exactly where three of the five bugs live (#1, #2, and by extension the off-by-one in #5's slicing).
- **`ValueError` is the only error-signaling convention** service functions raise; routes catch it uniformly and turn it into a 400/404. There's no custom exception hierarchy.
- **Association tables carry metadata** (`playlist_entries.position/added_by/added_at`), so queries against many-to-many relationships routinely need an explicit `.join()` back to the association table rather than just using the ORM-level `relationship()` — this is exactly the pattern `get_playlist_songs()` and `search_songs()` both use, and it's also where their respective bugs (#5's slice, #3's join fan-out) sit.

## Root Cause Analysis

### Issue #1 — My listening streak keeps resetting

**How I reproduced it.** Before touching any code, I ran the existing suite (`pytest tests/test_streaks.py -v`). Four tests passed but `test_streak_increments_on_sunday` failed: it sets a user's `last_listened_at` to a Saturday, calls `update_listening_streak` again with a Sunday timestamp exactly one day later, and asserts the streak goes from 1 to 2. The actual result was `1` — a bare reset, exactly matching kenji's report of a 12→1 drop on a Sunday. This confirmed the bug exists and is specifically tied to the day-of-week, not just "any day boundary" (the Monday→Tuesday consecutive-day test right above it passed fine).

**How I found the root cause.** The README pointed straight at `services/streak_service.py`, and it's a single ~35 line function (`update_listening_streak`), so there was no call-chain tracing needed — I read the whole function top to bottom. The logic branches on `days_since_last`: 0 → no-op, 1 → increment, else → reset. Line 73 read `elif days_since_last == 1 and today.weekday() != 6:`. The moment I saw a `.weekday()` check bolted onto what should be a pure "was it exactly one day" comparison, I knew that was the actual condition being tested, since `weekday()` returning `6` means Sunday in Python (Monday=0…Sunday=6). I confirmed by hand-tracing the failing test's exact values: Saturday→Sunday has `days_since_last == 1` and `today.weekday() == 6`, so the `and` clause evaluates to `False`, sending it to the `else` branch.

**The root cause.** The increment branch required `days_since_last == 1 AND today.weekday() != 6`. That second clause has nothing to do with correct streak logic — it excludes Sundays specifically from ever being treated as a consecutive-day increment, no matter how many days in a row the user actually listened. Any streak that reaches a Sunday with `days_since_last == 1` gets routed into the `else: user.listening_streak = 1` branch instead, which is indistinguishable from actually skipping a day. That's precisely why kenji saw the reset on Sundays specifically and why listening again on Monday started counting from 1 again (Monday's `weekday() != 6` is `True`, so *that* increment worked normally, masking the fact that the previous day's increment was wrongly suppressed).

**My fix and side-effect check.** I removed the `and today.weekday() != 6` clause entirely, leaving `elif days_since_last == 1: user.listening_streak += 1`. This is the smallest possible change — the day-of-week was never a legitimate input to this decision. After the fix, all 5 tests in `test_streaks.py` pass, including the ones that weren't touching Sunday at all (`test_streak_starts_at_1_for_new_user`, same-day no-op, and the skipped-day reset test), confirming the fix didn't loosen the "skip a day → reset" rule or the "same day → no change" rule on either side of the boundary — it only removed the spurious Sunday exception.

### Issue #5 — The last song in a playlist never shows up

**How I reproduced it.** Ran `pytest tests/test_playlists.py -v` before making any change. `test_playlist_returns_all_songs` seeds a playlist with 5 songs and asserts `get_playlist_songs()` returns 5 — it returned 4. `test_playlist_returns_songs_in_order` failed too, missing exactly `"Track 5"` (the highest-position song) from the end of the list. This matched darius's report precisely: "Friday Energy" says 7 songs but shows 6, and the missing one is always the most recently added.

**How I found the root cause.** README pointed at `services/playlist_service.py`. `get_playlist_songs()` builds a `songs` list via a join against `playlist_entries` ordered ascending by `position` — so far correct, and it explains *why* the missing song is always the most recent one (highest position = last in an ascending-sorted list). The last line was `return [song.to_dict() for song in songs[:-1]]`. Seeing a `[:-1]` slice applied to an already-correctly-ordered, already-complete list — right before it gets returned — was the moment I was confident this was the actual bug and not just a suspicious area: there's no reason for that slice to exist given everything above it already produces the right list.

**The root cause.** `songs[:-1]` unconditionally drops the last element of the ordered song list before serializing it. Since the list is sorted ascending by `position`, the last element is always the song with the highest position — i.e. whichever song was added most recently. This is a straightforward off-by-one/stray-slice bug, not a query or ordering issue: the SQL and ordering were already correct, and the function silently truncated a correct result right before returning it. That also explains darius's "adding a new song frees the previous one" observation: each new song claims the highest position, so it becomes the one sliced off, while the previously-hidden song (now no longer last) becomes visible.

**My fix and side-effect check.** Changed `songs[:-1]` to `songs` — no other logic needed to change, since the query and ordering were already correct. After the fix, all 3 playlist tests pass: `test_playlist_returns_all_songs` (count), `test_playlist_returns_songs_in_order` (ordering, including the previously-missing last position), and `test_empty_playlist_returns_empty_list`. That last one matters as a boundary check: an empty list run through `[:-1]` in Python doesn't raise, it just silently stays empty (`[][:-1] == []`), so the empty-playlist case was already accidentally "correct" before my fix and stayed correct after — confirming I didn't regress the zero-songs edge case while fixing the many-songs case.

### Issue #4 — I got notified when a friend added my song to a playlist but not when they rated it

**How I reproduced it.** No existing test file covers `notification_service.py`, so I wrote a throwaway script: created a `sharer` and a `rater` user and a `Song` owned by `sharer`, called `rate_song(rater.id, song.id, 5)`, then called `get_notifications(sharer.id)`. Result: `0` notifications, an empty list — exactly matching aaliya's report that the rating saves fine but nothing shows up in her notification list.

**How I found the root cause.** README pointed at `notification_service.py`. I read the whole file, which has four functions: `create_notification` (the low-level constructor), `add_to_playlist`, `rate_song`, and `get_notifications`. `add_to_playlist` is the *working* case the issue explicitly contrasts against, so I read it first: it appends the song to the playlist, commits, and then has a final block — `if song.shared_by != added_by_user_id: create_notification(...)`. I then read `rate_song` line by line looking for the equivalent block and there isn't one: it validates the score, loads the song and rater, finds-or-creates the `Rating`, commits, and returns. There's no `create_notification` call anywhere in the function, and no dead/disabled code suggesting one was ever removed. That absence — not a broken condition, but a step that plain doesn't exist — is what the hint meant by "architectural, not a typo."

**The root cause.** `rate_song()` and `add_to_playlist()` are meant to follow the same pattern: perform the action, then notify `song.shared_by` if the person who acted isn't the sharer themselves. `add_to_playlist()` implements that whole pattern. `rate_song()` only implements the first half (save the `Rating`) and was never given the second half (notify the sharer). It's not that a condition is wrong or a field is misnamed — the function that should exist to close this gap (something like "on rate, notify the sharer") was simply never written, even though the `Rating` model, the `create_notification()` helper, and the `song.shared_by` field it would need were all already in place.

**My fix and side-effect check.** After `rate_song()` commits the rating, I added the same shape of check `add_to_playlist()` uses: `if song.shared_by != user_id: create_notification(user_id=song.shared_by, notification_type="song_rated", body=f"{rater.username} rated your song '{song.title}' {score} stars.")`. I wrote `tests/test_notifications.py` (no such test file existed before) covering: a friend's rating notifies the sharer; rating your *own* shared song does not self-notify (mirroring the same guard `add_to_playlist` uses); and re-rating an already-rated song (the update branch of `rate_song`, not just the insert branch) still fires a notification each time. All three pass. While writing a fourth sanity-check test for the pre-existing `add_to_playlist` path, I discovered a separate, out-of-scope bug: `add_to_playlist()`'s `playlist.songs.append(song)` doesn't populate the `position`/`added_by` NOT NULL columns on the `playlist_entries` association table, so it raises `IntegrityError` any time it needs to insert a song that isn't already in the playlist. That bug isn't one of the 5 tracked issues and I did not fix it, but I adjusted that one test to pre-insert the association row directly (bypassing the buggy append) so it could still verify the notification half of `add_to_playlist` is unaffected by my change.

### Issue #2 — Friends Listening Now shows people from yesterday

**How I reproduced it.** No existing test covers `feed_service.py`, so I wrote a script: created two friended users, a song, and a `ListeningEvent` for the friend timestamped at "yesterday, 23:00 UTC" (computed relative to the real current time, so it's always a genuinely different calendar date but under 24 real hours old). I ran `get_friends_listening_now(me.id)` immediately afterward (real current time was ~04:49 UTC, so the event was ~5.8 hours old). It returned 1 entry — the friend's yesterday-evening listen showed up as "listening now," reproducing nova's report exactly (checked ~9am, friend's last listen was ~11pm the night before).

**How I found the root cause.** README pointed at `feed_service.py`. `get_friends_listening_now()` is short: it computes `cutoff = datetime.now(timezone.utc) - RECENT_THRESHOLD` where `RECENT_THRESHOLD = timedelta(hours=24)`, then filters `ListeningEvent.listened_at >= cutoff`. I compared it against the sibling function `get_activity_feed()`, whose docstring explicitly says it is "not filtered by recency," which told me `get_friends_listening_now` is the one place recency filtering is supposed to happen correctly. The docstring for `get_friends_listening_now` itself says "listened to something recently... or at least what they've played today" — but the code implements "within the last 24 hours," which is a materially different rule than "today." A rolling 24-hour window and a calendar-day window only agree at exactly midnight; any other time of day, the rolling window includes part of yesterday.

**The root cause.** `RECENT_THRESHOLD = timedelta(hours=24)` combined with `cutoff = now - RECENT_THRESHOLD` implements "happened within the last 24 real hours," not "happened today." An event timestamped 11pm yesterday stays `>= cutoff` continuously until 11pm *today* — a full 24 hours after it happened — regardless of the fact that the calendar date has already changed at midnight. That's exactly why nova saw darius's 11pm event still present at 9am (only ~10 hours old, well inside the 24h window) and why the report says stale entries "hang around... until the same time the next day": the window's expiry is pinned to the event's own timestamp plus 24 hours, not to the start of the current day.

**My fix and side-effect check.** I changed the cutoff calculation from a rolling window to a calendar-day boundary: `cutoff = datetime.combine(now.date(), time.min, tzinfo=timezone.utc)` (midnight UTC of the current day), and removed the now-unused `RECENT_THRESHOLD` constant and the `timedelta` import it required. I wrote `tests/test_feed.py` covering both sides of the boundary: an event at yesterday 23:00 now correctly returns an empty feed, and an event at today 00:01 still correctly appears. I also reran the full suite (`pytest tests/`, 19 tests) to confirm `get_activity_feed()` — which intentionally shares the `ListeningEvent` model and friend-lookup logic but doesn't do recency filtering at all — was untouched by this change, since I only edited `get_friends_listening_now()`.

### Issue #3 — The same song keeps showing up twice in search

**How I reproduced it — and an important honest caveat.** I ran `pytest tests/test_search.py -v` first, expecting `test_search_no_duplicates_multi_tag_song` (which explicitly comments "Should be 1, bug causes it to be 3") to fail. It passed. I then called `search_songs("Anthem")` directly against the real seeded database (`python seed_data.py` then a script calling the service function), and separately hit the live endpoint with `curl "http://127.0.0.1:5099/songs/search?q=Anthem"` after starting the app with `flask run`. Both returned exactly 1 result for "Crown Heights Anthem," which has 3 tags in the seed data specifically to expose this bug. So: as literally executed end-to-end in this environment (`SQLAlchemy 2.0.51`, pinned only as `>=2.0.0` in `requirements.txt`), the reported duplication does not appear. I did not stop there, because "the test passes" isn't the same as "the code is correct" — I wanted to understand *why* it didn't reproduce before deciding it wasn't a bug.

**How I found the root cause.** `search_songs()` in `search_service.py` builds `db.session.query(Song).outerjoin(song_tags, Song.id == song_tags.c.song_id).filter(...).all()`. The `filter()` only ever tests `Song.title`/`Song.artist` — `song_tags` is never referenced in the `WHERE` clause, which made the join immediately suspicious: it can't be doing any filtering work. I inspected the compiled SQL directly (`str(query)` and `db.session.execute(query.statement).fetchall()`) rather than the ORM-wrapped `.all()` result, and got 3 raw rows back for the 3-tagged song — one per matching `song_tags` row, the classic join fan-out. But `db.session.query(Song)...all()` (the ORM-level call the service actually makes) returned only 1. I confirmed this is because SQLAlchemy's legacy `Query` API (`session.query(Entity)`) implicitly de-duplicates result rows by primary key when the query loads a single full mapped entity with no extra selected columns — a long-standing ORM behavior originally meant to support eager-loaded collections without producing duplicate parent objects. Since `search_songs()` selects only `Song` columns, that implicit de-dup silently absorbs the fan-out before the list reaches `to_dict()`.

**The root cause.** The `outerjoin(song_tags, ...)` in `search_songs()` is dead weight: it doesn't filter on tags, and `Song.tags` is already loaded separately via the `lazy="subquery"` relationship for serialization. At the SQL level, joining to an association table with a one-to-many-per-song shape (one `song_tags` row per tag) multiplies each matching song into one row per tag it has — a song with 3 tags produces 3 SQL rows for a single logical match, which is exactly why the seed data groups songs into 0/1/3+ tag buckets: only the 3+ tag bucket would visibly reproduce this as duplicates. In this specific SQLAlchemy version, the ORM's implicit uniquing on plain entity loads happens to absorb that fan-out before it reaches the caller, so the user-visible symptom doesn't currently occur through this exact code path. That masking is incidental, not intentional — the query would duplicate immediately if it added `.limit()`/`.offset()` for pagination (a natural next feature for a search endpoint under this fan-out, some paging strategies interact badly with implicit uniquing), used 2.0-style `select()` + `session.execute()` instead of legacy `session.query()`, or ran against an older SQLAlchemy release. Relying on an unrelated ORM implementation detail to hide a join that shouldn't be there is itself the bug.

**My fix and side-effect check.** I removed the `outerjoin(song_tags, ...)` call entirely (and the now-unused `Tag`/`song_tags` imports), since it filtered nothing and only introduced fan-out risk. This is a stronger fix than adding `.distinct()`, because it eliminates the row multiplication at the SQL level instead of depending on the ORM (or a `DISTINCT` clause, which itself can behave surprisingly with joined columns) to clean it up afterward. After the fix, all 5 `test_search.py` tests still pass, and I re-verified against the real seeded DB that `search_songs("Anthem")` still returns the song with its full `tags: ["rap", "hip-hop", "boom bap"]` list intact — confirming tag data is unaffected since it was never dependent on that join in the first place.

**AI disclosure for this one specifically:** once I'd already found the suspicious join and reproduced the raw-SQL fan-out myself, I asked Claude to explain the difference between SQLAlchemy's legacy `Query.all()` and 2.0-style `select()`/`Result.unique()` de-duplication semantics, to confirm my hypothesis about *why* the ORM call returned 1 instead of 3. I verified that explanation against the actual installed SQLAlchemy behavior with my own script before relying on it.
